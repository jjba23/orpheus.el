This page is for the reader who wants to know why the package is shaped the
way it is.  It is not required to use the player.  The short version is that
Emacs owns the interface, a backend owns the music, and processes, timers and
text properties do the rest.  The diagrams below are Mermaid, so GitHub,
GitLab and an Org export with Mermaid support can draw them; the source stays
readable as plain text everywhere else.

* The seam
:PROPERTIES:
:CUSTOM_ID: the-seam
:END:

The queue, the tabs, the keys and the drawing know nothing about MPD, mpv or
SSH.  They call the generics in =orpheus-backend.el=; a backend implements
those and appears in the same interface.  That is the whole reason one player
can show a daemon, a folder and another machine without three interfaces.

#+begin_src mermaid
flowchart LR
  User["keys, mouse, M-x"] --> UI["player buffer<br/>tabs, list, header line"]
  UI --> Core["orpheus.el<br/>queue and transport"]
  Core --> Mode["mode line<br/>global-mode-string"]
  Core --> Backend{"backend"}
  Backend -->|mpd| MPD["MPD client"]
  MPD --> Daemon[("mpd daemon")]
  Backend -->|local| Local["local backend"]
  Local --> MPV["mpv<br/>JSON IPC"]
  Backend -->|ssh| SSH["SSH backend"]
  SSH --> Remote[("remote files")]
  SSH --> Cache[("local cache")]
  Cache --> MPV
  Backend -->|spotify| SP["Spotify client"]
  SP --> Web[("Spotify Web API")]
  Web --> Device[("a Spotify device<br/>plays the audio")]
  MPV --> Audio[("system audio")]
  Daemon --> Audio
#+end_src

A backend answers questions and takes commands.  It does not draw a row, own a
key or decide where a tab goes.  The interface is a plain Emacs buffer, so the
same text is a list in a terminal, a mouse target in a graphical frame and a
buffer over SSH.  A new backend is a ~cl-defstruct~ and a handful of methods,
not a second player; [[file:backends.org#adding-one][Adding one]] shows the skeleton.

The queue lives where it can be authoritative.  MPD owns its queue in the
daemon; Spotify's queue lives on Spotify and is moved through the Web API; the
local and SSH backends keep it in Emacs, because there is no daemon
on the far side to keep it for them.  That is also why MPD can be gapless while
the local backend plays one file at a time.

* The backend lifecycle
:PROPERTIES:
:CUSTOM_ID: backend-lifecycle
:END:

Connecting is a callback, never a wait.  The chosen backend is built from the
registry, starts its player and its work, and calls back when it can answer.
The local backend starts the library watch before mpv, so a change during
startup is not missed, then retries the IPC endpoint every 50 ms until mpv
answers or about five seconds have passed.  Disconnecting is the reverse: the
watches go first, then the process.

#+begin_src mermaid
sequenceDiagram
    participant U as orpheus-connect
    participant R as backend registry
    participant B as local backend
    participant M as mpv
    participant W as file notifications
    U->>R: make the chosen backend
    U->>B: connect(callback)
    B->>W: watch the library tree
    B->>M: spawn with --input-ipc-server
    loop until the socket or pipe answers
        B->>M: connect IPC
    end
    M-->>B: JSON events
    B-->>U: connected
    U->>B: disconnect
    B->>W: remove every watch
    B->>M: stop the process
#+end_src

The SSH backend has the same shape with an ssh process and a download queue
instead of mpv; MPD connects its socket and reads the greeting.  A backend
that cannot connect calls back with nil, so the interface says so instead of
showing a player that is not there.

Spotify has no process to start, so connecting means having a token the API
still accepts:

#+begin_src mermaid
sequenceDiagram
    participant O as orpheus
    participant S as Spotify backend
    participant A as accounts.spotify.com
    participant W as api.spotify.com
    participant D as your device
    O->>S: connect
    S->>S: read orpheus-spotify-token-file
    opt the access token has run out
        S->>A: refresh_token grant
        A-->>S: a new access token, written 0600
    end
    S-->>O: connected
    loop every orpheus-spotify-poll-interval
        S->>W: GET /me/player
        W-->>S: the status and the track, one reply
    end
    O->>S: play, next, seek
    S->>W: PUT or POST /me/player/...
    W-->>D: the device plays
    Note over S,W: a 429 stops the requests until Retry-After
#+end_src

The sign-in itself is the one part with no counterpart in the other backends:
~orpheus-spotify-login~ sends the browser to the account page with a PKCE
challenge, listens on the loopback redirect URI for the single request that
carries the code, and swaps that code for a token.  Nothing else in the player
knows about it, because the token file is what every later request reads.

* One disc image, many tracks
:PROPERTIES:
:CUSTOM_ID: disc-images
:END:

A CD ripped as one file carries its track boundaries outside the audio: in a
~.cue~ file beside it, in a ~CUESHEET~ Vorbis comment, or in the binary
~CUESHEET~ block of a FLAC file.  Browsing reads that sheet and makes one row
per track, with the track number, title, artist and length.  Playing a row
seeks to its minutes and stops at its end; the position shown counts within
the track, not within the whole disc.

#+begin_src mermaid
flowchart TD
  File["disc.flac"] --> Sheet{"sidecar .cue<br/>FLAC CUESHEET tag or block"}
  Sheet -->|tracks| Rows["one row per track"]
  Rows --> Pick["choose track 02"]
  Pick --> Local["local: mpv --start=... --end=..."]
  Pick --> Host["SSH host with ffmpeg:<br/>cut there, send the minutes"]
  Pick --> Range["SSH host without ffmpeg:<br/>dd the byte range, cut here"]
#+end_src

The range travels in the URI as a fragment, so a queue entry, a playlist and a
cache key all keep it without a second data structure.  The local backend reads
a sidecar first, then a FLAC ~CUESHEET~ Vorbis comment, then the binary block;
SSH reads the sidecar.
The cue title and artist are remembered, so the queue and the now-playing card
name the song instead of the image file.

Over SSH the chosen track is cut on the host with ~ffmpeg~ when it is there,
remuxed rather than re-encoded, so only its minutes cross the link.  Without
it, the FLAC seek table (or an estimate from the average bitrate) names the
byte range, GNU ~dd~ on the host fetches only those bytes, and this machine's
~ffmpeg~ cuts the track; ~ffprobe~ corrects an estimate.  The last track has
no end and works the same way.  Only an image with no usable range is copied whole once, and
every track of that disc plays from that copy; ~orpheus-ssh-split-images~ nil
asks for that copy explicitly.

A search reads a sidecar ~.cue~ beside the image, so a song title finds its
track.  Locally, a FLAC with no sidecar is served from an embedded-cue cache:
the first search returns whatever the cache has at once and indexes the FLACs
in its result in small background batches, then refreshes the tab.  The index
is keyed by path, size and modification time, so a normal search is a lookup
and a stat per FLAC rather than opening every file.  Titles come from a
~CUESHEET~ Vorbis comment; the binary ~CUESHEET~ block supplies track
boundaries but has no titles.  Browsing a local FLAC uses the same cache, and
the header line shows ~indexing cues n/m~ while the background run is in
flight.  The cache file is versioned and replaced through a temporary file, so
an interrupted write leaves the previous index intact.  Loading the cache
prunes entries for files that are gone or changed, so a removed title is not
served; ~M-u~ prunes on demand and ~M-U~ clears the index.  Either library
command also drops the cached tab rows and covers.  The local backend watches
every library directory with file notifications, so an external change prunes
the cache and runs ~orpheus-backend-library-changed-hook~ on its own; the hook
is what drops the cached tabs and covers.  A directory the system cannot watch
still falls back to the on-access checks.  SSH reads sidecar ~.cue~ files only.

* Search matches songs, not only files
:PROPERTIES:
:CUSTOM_ID: search
:END:

Every backend returns rows, and the matching is shared.  A row matches when
the query is in its label or URI, or in the title, artist or album of the
track it carries.  A matching track yields only that track of the image; a
matching image name yields every track of that disc.  The interface therefore
does not need three search behaviors that drift apart.

#+begin_src mermaid
sequenceDiagram
    participant E as Emacs
    participant F as find or ls
    participant C as cue reader
    participant S as shared filter
    E->>F: list files below the root
    F-->>E: paths, including .cue files
    E->>C: parse sidecar and cached embedded cue sheets
    C-->>E: titles, artists, starts and ends
    E->>S: rows and query
    S-->>E: matching rows
    Note over E,S: A title returns its track; an image path returns the disc.
#+end_src

MPD searches its library through the daemon.  The local backend runs GNU
~find~ as a process, so a large tree does not block Emacs; on Windows, whose
~find.exe~ is a text-search program rather than a file lister, or on a host
with no GNU ~find~, it walks the tree with ~directory-files-recursively~
instead.  That fallback is synchronous, so a very large library can pause for
a moment; it is the price of a portable search with no extra program.  SSH
runs ~find~, and when the host has no ~find~ it falls back to a recursive
~ls~.  In both remote cases the cue sheets in the result are fetched one ~cat~
each, grouped by directory, so a restricted shell with no loops still answers.

* The library watcher
:PROPERTIES:
:CUSTOM_ID: library-watcher
:END:

File notifications are not recursive, so the local backend walks the library
once and keeps one watch per directory.  Events are coalesced for half a
second, because one save often produces several; then the cue cache is pruned,
saved if it changed, and the library hook tells the interface to drop its
cached tabs and covers.  A directory the system refuses to watch is not an
error: the on-access checks still catch a changed file, and ~M-u~ and ~M-U~
remain the manual repair.

#+begin_src mermaid
flowchart TD
  Connect["connect"] --> Walk["walk the library tree"]
  Walk --> Watch["one file-notify watch per directory"]
  Watch --> Event{"created, changed, deleted or renamed"}
  Event -->|created directory| Add["add watches below it"]
  Event -->|deleted or renamed directory| Remove["remove watches below it"]
  Event -->|file or directory change| Debounce["coalesce for 0.5 s"]
  Add --> Debounce
  Remove --> Debounce
  Debounce --> Prune["prune changed and missing cue entries"]
  Prune --> Save["save the cache when it changed"]
  Save --> Hook["run orpheus-backend-library-changed-hook"]
  Hook --> Tabs["drop cached tabs and covers"]
  Watch -->|watch refused| Fallback["keep serving with on-access checks"]
#+end_src

The watch tree skips hidden and symlinked directories, so a link back up the
tree cannot make the walk endless.  New directories are added when the event
arrives; deleted and renamed ones lose their watches, and a renamed directory
gets a new set at its new path.  The hook is a backend-neutral seam: another
backend can report a library change the same way without knowing about the
player's tabs.

* The event loop
:PROPERTIES:
:CUSTOM_ID: event-loop
:END:

Nothing waits for a socket.  MPD replies, mpv's JSON, SSH's listings, transfers
and cava's frames all arrive in process filters or sentinels.  One timer reads
the status; the list is redrawn only when something it shows changed.  The
header line and the mode line are functions over the same state, so a redraw
does not move point or the scroll position.  The local and SSH queue is
Emacs's, so the end of a file is what moves it forward.

#+begin_src mermaid
sequenceDiagram
    participant U as player buffer
    participant C as orpheus core
    participant B as local backend
    participant M as mpv
    participant T as status timer
    U->>C: RET on a row
    C->>B: play-uri or add
    B->>B: ensure mpv is running
    B->>M: loadfile with start and end
    M-->>B: file-loaded and metadata
    T->>B: status every second
    B->>M: time-pos, pause, volume
    M-->>B: properties
    B-->>C: status and track
    C-->>U: header, mode line, list if it changed
    M-->>B: end-file eof
    B->>B: advance the queue
    B->>M: loadfile the next entry
#+end_src

#+begin_src mermaid
flowchart LR
  P["process filters<br/>MPD, mpv, SSH, cava"] --> State["status and queue"]
  T["one-second timer"] --> State
  State --> H["header-line-format"]
  State --> M["global-mode-string"]
  State --> L["list redraw when it changed"]
  M --> C["text properties<br/>mouse-1 -> command"]
#+end_src

Emacs is a good host for this because it already has the pieces:

- *Processes are asynchronous by default.*  ~make-process~ and
  ~make-network-process~ deliver chunks to a filter, so a slow server cannot
  block the editor.  There are no worker threads and no locks; callbacks run on
  the same event loop as the keys.
- *A buffer is a layout engine.*  Faces, text properties and overlays draw the
  tabs, the list, the progress bar and the buttons.  A mouse click is a key
  lookup on the text under the pointer, not a separate GUI toolkit.
- *The mode line is a variable with a face.*  ~global-mode-string~ lets a
  global minor mode show the track in every buffer.  Each transport glyph gets
  its own small ~local-map~, so one click can run one command without changing
  the buffer you are editing.
- *Frames are ordinary objects.*  ~make-frame~ is enough to detach the player;
  the window manager moves and closes it like any other Emacs frame.
- *A terminal is a first-class display.*  ~display-graphic-p~ is the only test
  that matters for images and SVG; the text, the progress bar and the ASCII
  fallbacks work without a display server.

* Formats
:PROPERTIES:
:CUSTOM_ID: formats
:END:

The local and SSH backends use the same extension list,
~orpheus-local-extensions~.  It is deliberately a broad list of containers mpv
can open, not a promise that every codec inside every container is installed.
Tags, duration and cover art come from the file when they are there.

| Group     | Common extensions | What orpheus does |
|-----------+-------------------+------------------|
| Audio     | ~mp3~, ~mp2~, ~flac~, ~ogg~, ~oga~, ~opus~, ~m4a~, ~m4b~, ~aac~, ~wav~, ~aiff~, ~wma~, ~alac~, ~ape~, ~wv~, ~tta~, ~dsf~, ~dff~, ~mid~, ~midi~, ~amr~, ~ac3~, ~dts~, ~mka~, ~caf~, ~au~ | played by mpv; tags and cover art are read where the file provides them |
| Video     | ~mp4~, ~m4v~, ~mkv~, ~webm~, ~avi~, ~mov~, ~mpg~, ~mpeg~, ~ogv~, ~ts~, ~m2ts~, ~mts~, ~flv~, ~wmv~, ~vob~, ~3gp~, ~3g2~, ~rm~, ~rmvb~, ~divx~, ~asf~ | *sound only*: mpv starts with ~--no-video~ and ~--force-window=no~, so no video window opens |
| Playlists | ~m3u~, ~m3u8~ | listed and played as lists; orpheus writes portable M3U8 |

MPD does not use this list: it asks its daemon, so a format is available when
the daemon's own build supports it.  A cue sheet is not a format mpv decodes;
it is read in Emacs and turned into track ranges.

* Platforms
:PROPERTIES:
:CUSTOM_ID: platforms
:END:

The Emacs Lisp is the same everywhere; the program that plays the audio and the
program that lists the files are not.  The player degrades by dropping a
feature, not by failing to open.  The [[file:platforms.org][cross-platform guide]]
expands this table into setup checklists and a clear statement of what the
gate verifies.

| Feature | GNU/Linux | macOS | Windows |
|---------+-----------+-------+---------|
| Playback | mpv with PipeWire, PulseAudio or ALSA | mpv with CoreAudio | mpv with WASAPI over a per-Emacs named pipe; compiled but unproven |
| MPD | TCP or a Unix socket | TCP or a Unix socket | TCP; use ~orpheus-mpd-host~ and ~orpheus-mpd-port~ |
| SSH | OpenSSH, optional multiplexing | OpenSSH, optional multiplexing | OpenSSH client; multiplexing off on native Windows; the remote host must offer a POSIX shell |
| Search | asynchronous GNU ~find~ | asynchronous BSD ~find~ | Windows ~find.exe~ searches text, so Emacs walks the tree synchronously |
| Library watch | one watch per directory; on-access fallback | one watch per directory; on-access fallback | one watch per directory when the Emacs build has ~w32notify~; on-access fallback |
| Visualizer | cava with PipeWire by default; use ~pulse~ on PulseAudio-only systems | cava with PortAudio; a loopback device is needed for system output | cava captures the default output with no input method; availability varies |
| Cover art | images in a graphical frame | images in a graphical frame | images in a graphical frame; the scan runs in Emacs |
| Detach | a new graphical frame | a new graphical frame | a new graphical frame; a terminal says it needs a display |
| Terminal | text, Unicode and ASCII fallbacks | same | same |

Windows behavior is covered by unit tests that bind ~system-type~: the named
pipe carries the Emacs pid, art and search refuse Windows ~find.exe~, cava's
input section is omitted, and SSH multiplexing is disabled.  Local path
comparisons follow the filesystem's case rule, while remote paths stay
case-sensitive.  No Windows machine runs in this gate, so mpv over the named
pipe and the cava binary remain unproven rather than called supported.  On
macOS, BSD ~find~ accepts the ~-maxdepth~ and ~-iname~ flags the art scan
uses.  The watcher uses
whatever directory notifications the Emacs build provides; when it provides
none, the on-access checks take over.  Everything else in the table is the
same code on every platform, with the external program doing the
platform-specific part.
