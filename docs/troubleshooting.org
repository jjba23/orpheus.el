A player that goes quiet is usually one check away from working again.  None
of the checks below change your music, and none of them need a restart
first.  Start with the player's own diagnostics: ~H~ opens the help buffer,
~?~ opens the command menu, and ~M-x orpheus-tutorial~ walks the happy path
again.  The sections are ordered from the connection outward, so you can
stop as soon as the sound comes back.

* The player says “not connected”

The header line is truthful: the backend has not completed its connection.
Check the backend before changing an option.

** MPD

#+begin_src shell
pgrep -a mpd
#+end_src

- No line of output means the daemon is not running; start it the way you
  usually do before changing anything in Emacs.
- The socket path in ~orpheus-mpd-socket~ must be the one in ~mpd.conf~, and
  the host and port are used when the socket is nil.
- A socket connection still uses ~orpheus-mpd-host~ and ~orpheus-mpd-port~ to
  find the matching password entry.  They must describe the same daemon even
  when the connection itself is a socket.
- On another machine, make sure the daemon listens on an address the network
  can reach and that the firewall allows the port.

** Local

#+begin_src shell
mpv --version
#+end_src

The local backend needs ~mpv~ on ~exec-path~.  If ~orpheus-local-directory~ is
wrong, the player opens but the files tab is empty; it does not prevent the
connection.  ~ffmpeg~ is optional here: it pulls a cover out of the file and
reads lyrics tags, and without it a cover file beside the track is still used
and a track is still played.

** SSH

Run ~M-x orpheus-ssh-diagnose~.  It reports which remote commands and shell
features work, and it is the first thing to include in a bug report.  If the
host asks for a passphrase, unlock the key first: ssh has no terminal in which
to prompt from inside Emacs, so start ~ssh music.example.org~ once in a shell.
A new host also needs its key in =~/.ssh/known_hosts= first; use
~orpheus-ssh-extra-args~ with ~StrictHostKeyChecking=accept-new~ only once, not
as a permanent setting.

The table lists ~ffmpeg~ last on the host's side.  With it, a track of a CD
image is cut out on the host and only its minutes are copied.  Without it,
orpheus fetches a byte range planned from the FLAC seek table (or estimated
from the average bitrate) with ~dd~ and cuts the track here with this
machine's ~ffmpeg~; ~ffprobe~ corrects an estimate.  If ~dd~, local ~ffmpeg~
or a usable seek table is missing, the whole image is copied once, cached, and
the tracks play from that copy; ~orpheus-ssh-split-images~ nil asks for that
copy explicitly.  Either way the track is listed, because the ~.cue~ beside
the image is what names it.

If ssh reports ~ControlPath too long~ or ~too long for Unix domain socket~,
orpheus retries the command without multiplexing, so the listing still works.
Set ~orpheus-ssh-control-directory~ to a short private directory when the
default under ~$XDG_RUNTIME_DIR~ or =/tmp= is unsuitable, or set
~orpheus-ssh-multiplex~ nil to stop sharing connections entirely.  To rule out
the whole backend without restarting Emacs, press ~B~ in the player (or run
~M-x orpheus-switch-backend~).

* Search does not find a song inside a disc image

The local and SSH backends read a ~.cue~ file beside an image and list its
sheet as one row per track.  Search matches the track title, artist and album
as well as the row and file path, so a matching song returns its track and a
matching image name returns every track of that disc.  If the title is not
found:

- Check that the sheet is a sidecar ~.cue~ with the image's base name, such as
  =disc.cue= next to =disc.flac=.  Locally, a FLAC with no sidecar is indexed
  from its embedded cue sheet: the first search returns cached rows and
  indexes the FLACs in the result in the background, then refreshes the Search
  tab.  Titles need a ~CUESHEET~ Vorbis comment; a binary ~CUESHEET~ block has
  track boundaries but no titles.  The header shows ~indexing cues n/m~ while
  the background index runs, and a new or changed file is indexed again on the
  next search.
- If a removed or retitled image still appears, ~M-u~ prunes cue entries for
  files that are gone or changed; ~M-U~ clears the local cue cache and also
  drops cached tab rows and covers.  ~g~ only rereads the current tab.
- On SSH, only sidecar ~.cue~ sheets are read; an embedded FLAC cue is not
  searched.  Add a sidecar with the image's base name when a remote title must
  be searchable.  The sheets are fetched with one ~cat~ per sheet.  If the
  remote shell rejects ~cat~, ~M-x orpheus-ssh-diagnose~ shows it; the disc is
  still
  listed, but its track titles cannot be searched until the sheet is readable.
- A host without ~find~ searches with a recursive ~ls~, and a Windows local
  search walks the tree in Emacs.  Both fallbacks are slower on a very large
  library, but they return the same rows.
- MPD searches its daemon's index, not a cue sheet on this machine; the cue
  rows above belong to the local and SSH backends.

* A password is rejected

~orpheus-mpd-password~ nil means the password comes from ~MPD_PASSWORD~ first,
then from ~auth-source~.  A password that is found is sent; a daemon with no
password answers an incorrect-password error to a password it never requested,
so keep the auth store to the daemons it describes.  The machine and port in
the entry must match ~orpheus-mpd-host~ and ~orpheus-mpd-port~.

The setup recipe and the ~pass~ integration are in [[file:usage.org][Using orpheus]].
If the connection fails immediately after a password change, read the auth
entry back rather than trusting the command's exit status.

* Why MPD's queue is already full at the start

The queue is the daemon's, not the player's: orpheus sends ~add~, ~delete~ and
~clear~ and reads ~playlistinfo~ back, so the Queue tab shows what MPD holds.
MPD writes that queue into its ~state_file~ when it stops and reads it back
when it starts, which is why the first Queue tab of the day can be full while
nothing was added to it.  orpheus adds nothing on start.

~D~ empties the queue, and an ~mpd.conf~ without a ~state_file~ makes the
daemon forget it at shutdown.  The local backend is the other way round: Emacs
keeps that queue, so it starts empty in every session.

* Downloads do not start or do not finish

- The remote shell must accept the quoted commands the backend sends.  Run
  ~M-x orpheus-ssh-diagnose~ and look for the command that fails.
- If ~cat~ is unavailable, the transfer falls back to ~sftp~.
  ~orpheus-ssh-sftp-program~ must name a program installed on this machine, and
  ~orpheus-ssh-sftp-extra-args~ carries its options, such as ~-P 2222~.
- A key that works in a shell may still fail here if it needs a passphrase.
  Unlock it first.
- Playback starts only after the copy is complete.  A large track spends its
  transfer time downloading; the Downloads tab shows the bytes and the ETA.
- ~d~ cancels the selected transfer.  A failed transfer can be retried with
  ~RET~ after the cause is fixed.
- A directory change, a search and a cover lookup share one multiplexed ssh
  connection while downloads keep their own, so a slow answer is the link
  rather than a lock held by a transfer.  ~orpheus-ssh-multiplex~ turns the
  shared connection off on a host whose ssh does not support it.
- The cache is under ~orpheus-cache-directory~ (=~/.cache/orpheus= by
default).  If the disk is full, lower ~orpheus-cache-max-bytes~ and the
least recently used tracks and covers are dropped after the next transfer.
- A command that is owed a reply past its timeout is dropped and says so:
  ~orpheus-mpd-timeout~ for MPD and ~orpheus-ssh-command-timeout~ for
  listings, searches and covers.  Transfers are never timed out; cancel one
  with ~d~ if it really is stuck.

* There is no cover art

- Cover art is drawn only in a graphical frame.  A terminal is text on purpose;
  the list, card and progress bar still work.
- Local and SSH accept any image file in the track's folder, its parent and
  one level of child folders.  The names in ~orpheus-local-cover-names~ are
  tried first, so ~cover.jpg~ wins over a stray ~scan.jpg~, and
  ~orpheus-local-art-extensions~ decides what counts as an image.  A cover in
  the album root is found from a disc subfolder, and one in ~Scans/~ is found
  from the album.  The search runs off the main thread; SSH copies a remote
  cover into its cache.
- MPD supplies embedded ~albumart~ or ~readpicture~.  A daemon or file without
  either has no cover to draw.
- An image Emacs cannot decode is skipped.  If the file is unusual, convert it
  to JPEG or PNG.

* The visualizer is empty or missing

The visualizer is [[https://github.com/karlstav/cava][cava]], not a player-specific
meter.  It listens to the system output, so it shows whatever the machine is
playing.

- Check that ~cava~ is installed and that ~orpheus-vis-program~ names it.
- On GNU/Linux, cava captures the default PipeWire or PulseAudio monitor.  If
  the sink is not the one playing, select the right input with ~orpheus-vis-input~.
- On macOS, the default ~portaudio~ input records an input device.  Hearing
  system output needs a loopback device such as BlackHole; without one, playback
  works and the visualizer is silent.
- In a graphical frame the bars are SVG.  A frame without SVG support falls
  back to block characters, which is a real rendering rather than an error.

* The equalizer says MPD cannot do it

That is correct.  The equalizer applies an mpv audio filter, so it works with
the local and SSH backends.  MPD's audio leaves through the daemon's own
output; Emacs never sees the samples.  Use MPD's own output configuration or
switch to the local backend if the equalizer matters.

* Reporting a problem

Include the backend, the orpheus version (~orpheus-version~), the exact
options that differ from their defaults, and the output of
~M-x orpheus-ssh-diagnose~ for SSH problems.  Open an issue at
[[https://github.com/jjba23/orpheus.el/issues][github.com/jjba23/orpheus.el]].
Do not paste passwords, private keys or the contents of your auth store.
