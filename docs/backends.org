A backend is how orpheus reaches your music.  The player itself gives you the
window, the keys and the queue; the backend is the small part that knows how
to list files, read tags and start playback.  Three ship here, and they look
the same to use, so start with whichever one matches what you already have.
In the player, ~B~ (or ~M-x orpheus-switch-backend~) disconnects the current
backend and connects the chosen one, rebuilding the tabs without restarting
Emacs.

| Backend | Best for | Needs |
|---------+----------+-------|
| MPD     | an existing library and daemon, especially on another machine | ~mpd~ and a running daemon |
| local   | files and URLs on this machine | ~mpv~; ~ffmpeg~ for extracted covers, ~yt-dlp~ for video links |
| SSH     | a library on a remote machine with no daemon there | ~ssh~; ~sftp~ only when the remote shell cannot run ~cat~ |

The trade-off is where the queue lives.  MPD owns its queue in the daemon;
local and SSH keep the queue in Emacs, and SSH copies each track before mpv
plays it.  MPD can be gapless because it owns the whole queue; the local
backend plays one file at a time.  The visualizer is independent of all three:
it listens to the system output through cava.

** What a backend is
:PROPERTIES:
:CUSTOM_ID: what-a-backend-is
:END:

A backend is a ~cl-defstruct~ that includes ~orpheus-backend~ and implements
these generics from =orpheus-backend.el=:

| Generic                          | Meaning                                        |
|----------------------------------+------------------------------------------------|
| ~orpheus-backend-connected-p~    | is it ready to take commands?                  |
| ~orpheus-backend-connect~        | connect, then call back with the backend or nil |
| ~orpheus-backend-disconnect~     | close it                                       |
| ~orpheus-backend-status~         | an ~orpheus-status~: state, elapsed, total, volume, flags, song id |
| ~orpheus-backend-track~          | an ~orpheus-track~: URI, title, artist, album, duration, … |
| ~orpheus-backend-queue~          | the queue as ~orpheus-item~ rows                |
| ~orpheus-backend-browse~         | one tab's rows, for a kind and a path           |
| ~orpheus-backend-add~            | append URIs to the queue                       |
| ~orpheus-backend-play-uri~       | play a URI now                                 |
| ~orpheus-backend-portable-uri~   | store a URI as a library-relative path          |
| ~orpheus-backend-playlist-uri~   | resolve a playlist URI for the backend          |
| ~orpheus-backend-command~        | play, pause, toggle, stop, next, previous, seek, volume, repeat, random, single, consume, update, rescan, clear, shuffle, delete, save, playpos, playid, load |
| ~orpheus-backend-equalizer~      | set the mpv audio filter chain, or nil when the backend cannot || ~orpheus-backend-album-art~      | a file path to the cover, or nil |
| ~orpheus-backend-local-file~     | a local file the backend holds for a track, or nil |
| ~orpheus-backend-downloads~      | active and recent transfers as rows, when it has a ~downloads~ capability |
| ~orpheus-backend-cancel-download~ | cancel the transfer for a URI                 |
| ~orpheus-backend-capabilities~   | which of the browse kinds it can do            |

The browse kinds are ~queue~, ~downloads~, ~directories~, ~artists~,
~albumartists~, ~albums~, ~playlists~ and ~search~; the interface draws a tab
per kind a backend claims.  A row is an ~orpheus-item~ with a label, a detail column, a
kind, and an alist whose ~uri~ makes it playable and whose ~browse~ is a
~(KIND . ARG)~ to descend into.

Three backends are shipped and are the reference implementations:

- =orpheus-mpd.el= — a complete MPD client on ~make-network-process~: TCP or a
  unix socket, password, serialized replies, ~ACK~ errors, and the ~albumart~
  and ~readpicture~ binary payloads for cover art.  A daemon that owes a reply
  for ~orpheus-mpd-timeout~ seconds is dropped, and every command still waiting
  is answered with the reason instead of hanging the interface.
- =orpheus-local.el= — mpv over its JSON IPC socket, with the queue kept in
  Emacs, tags read from mpv's ~metadata~ property, cover art found next to the
  file or in its album folder, or extracted with ffmpeg, and URLs delegated to
  mpv (and so to yt-dlp).
- =orpheus-ssh.el= — remote files over ssh and mpv here: ~ls -1p~ fills the
  files tab, ~find~ fills Search, and ~cat~ streams the chosen track into the
  cache; a cover near the track's folder is copied to the same cache.  ~sftp~
  takes over when the shell rejects ~cat~.  A one-time check reports the remote
  commands and shell features.  Transfers run in a queue of at most
  ~orpheus-ssh-concurrency~, a play request goes ahead of the background
  prefetches, and the Downloads tab shows each one.  Listings, searches, size
  probes and covers share one multiplexed connection
  (~orpheus-ssh-multiplex~), while downloads keep connections of their own, so
  a slow link still answers a directory change.  The control socket is kept in
  a short private directory (~orpheus-ssh-control-directory~); a host that
  rejects it is retried once without multiplexing instead of failing the
  listing.  The local backend plays a copy
  once it is complete.  There is no daemon on the far side, and the cache is
  ordinary files under ~orpheus-cache-directory~: it survives a disconnect and
  a reboot, and ~orpheus-cache-max-bytes~ keeps it bounded.  A listing, search
  or cover command that stays silent for ~orpheus-ssh-command-timeout~ seconds
  is killed and reported; a transfer, which may legitimately take minutes, is
  never timed out.

** Adding one
:PROPERTIES:
:CUSTOM_ID: adding-one
:END:

Register a constructor and implement the generics:

#+begin_src emacs-lisp
(cl-defstruct (my-player (:include orpheus-backend)
                         (:constructor make-my-player)
                         (:conc-name my-player--))
  process)

(orpheus-register-backend 'my-player #'make-my-player
                          "My player, through its command line client")

(cl-defmethod orpheus-backend-connected-p ((backend my-player))
  "Return non-nil when the client is running."
  (process-live-p (my-player--process backend)))

(cl-defmethod orpheus-backend-command ((backend my-player) action &optional value)
  "Run ACTION on my player, with VALUE when it takes one."
  (ignore backend value)
  (pcase action
    ('toggle (my-player--call "play-pause"))
    ('next   (my-player--call "next"))))

(cl-defmethod orpheus-backend-capabilities ((_backend my-player))
  "This player knows a queue and a search, and nothing more."
  '(queue search))
#+end_src

Two things make a backend feel finished: it calls its callbacks from process
filters rather than from a blocking read, and it degrades by claiming fewer
capabilities instead of lying about them.  A skeleton like the one above needs
a ~my-player--call~ of your own: an asynchronous wrapper around the command
line client you drive.  No backend for a subscription service ships here,
because its sign-in belongs to your account, not to this repository.

** YouTube
:PROPERTIES:
:CUSTOM_ID: youtube
:END:

No extra backend is needed: with ~orpheus-backend~ set to ~local~, any URL mpv
can open plays —

#+begin_src emacs-lisp
(orpheus-play-url "https://www.youtube.com/watch?v=dQw4w9WgXcQ")
#+end_src

— and when ~yt-dlp~ is installed mpv uses it automatically.  Seeking and
metadata work where the extractor provides them.

* Platforms
:PROPERTIES:
:CUSTOM_ID: platforms
:END:

** GNU/Linux and PipeWire
:PROPERTIES:
:CUSTOM_ID: gnulinux-and-pipewire
:END:

MPD's own audio output is the PipeWire, PulseAudio or ALSA one you configured
in ~mpd.conf~; orpheus does not touch it.  The local backend asks mpv for
~--ao=pipewire,pulse,alsa~, so PipeWire is used when it is there and mpv falls
back by itself when it is not.  cava captures with ~method = pipewire~, the
monitor of the default sink, which is why the visualizer draws what any player
is playing.

** macOS
:PROPERTIES:
:CUSTOM_ID: macos
:END:

MPD uses CoreAudio.  The local backend asks mpv for ~--ao=coreaudio~, and
~orpheus-vis-input~ defaults to cava's ~portaudio~ input.  That input records
an *input* device, so hearing system output in the visualizer needs a loopback
device such as BlackHole; without one, MPD and mpv still play, and the
visualizer shows silence.  Cover art, notifications and the rest are the same
as anywhere else.

** Windows and everything else
:PROPERTIES:
:CUSTOM_ID: windows-and-everything-else
:END:

The local backend asks mpv for ~--ao=wasapi~ on Windows and drives it over a
named pipe; that path is written and compiled but untested, so treat it as
unproven rather than supported.  ssh multiplexing is left to OpenSSH; orpheus
gives it a short private socket directory and retries without multiplexing
when OpenSSH rejects it, so a path limit does not fail the listing.  With
~(setq orpheus-ssh-multiplex nil)~ the backend opens one connection per
command, as before.  MPD works wherever MPD does — that includes
an MPD on another machine, which is the case that needs no platform support at
all.  Nothing in the package reads or writes a path in a platform-specific way
beyond ~temporary-file-directory~ and ~orpheus-cache-directory~.
